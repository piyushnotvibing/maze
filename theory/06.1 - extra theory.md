The theory: why delete is the half everyone skips

Insert only ever has one failure mode: a page gets too full, so you split it and hand the parent one new separator. Delete has the mirror problem — a page gets too empty — but the textbook fix has two different repair operations depending on circumstance:

- Borrow from a sibling that has slack (cheap — no page freed, just one cell moves and the parent's separator shifts).
- Merge two siblings when neither has slack to lend (combines two pages into one, frees a page, and — this is the asymmetry that makes delete harder than insert — removes a separator from the parent instead of adding one).

That "remove instead of add" is the whole reason delete's parent-propagation step can't just be insert's propagation run backwards. Insert always makes the parent gain exactly one cell (possibly triggering a split). Delete always makes the parent lose a cell — and losing a cell can itself make that parent too empty, cascading upward exactly the way splits cascade upward on insert, just in the opposite direction.

How SQLite actually handles it

Worth knowing precisely, even though you're not building this version: SQLite doesn't have separate "borrow" and "merge" code paths at all. It reuses the same balance_nonroot routine insert uses — gather the underflowing page plus up to two siblings, dump all their cells into one combined list, decide how many output pages are needed to hold them at a healthy fill (which can be fewer than the input page count — that's what makes it a "merge" when the data's sparse, and effectively a "borrow" when it's just slightly uneven), and redistribute evenly across however many pages that turns out to be. Insert-overflow and delete-underflow are the literal same function, just landing on a different output count depending on the data. The mirror of balance_deeper (root split) is balance_shallower: if rebalancing ever leaves the root with exactly one child, that child's content gets copied back up into the root page itself, shrinking the tree by a level.

You're not building the gather-three-siblings version — that's real complexity for a feature real SQLite needed for performance, not correctness, and the plan deliberately asks for something much simpler.

The policy to adopt, stated precisely

Per the plan: tolerate underfull leaves entirely — no threshold, no borrowing. The only trigger for any rebalancing at all is a page having exactly zero cells. That's the whole policy. It's a good scope choice specifically because of how your code is already shaped: TablePage's insert_unchecked/fits/cells()/cells_mut() already give you everything you need to add a mirroring remove without inventing new machinery, and check_tree already exists as the oracle that'll catch you if the simplification goes wrong somewhere.

The concrete design — mirroring InsertOutcome almost symbol-for-symbol

This is the part worth being careful about, because there's a real asymmetry hiding in it that isn't obvious until you try to write the parent-level handling.

When a leaf becomes empty, it just vanishes — there's nothing in it, so nothing needs to replace the separator that used to route to it. The parent just removes that separator/pointer entirely.

When an interior page becomes empty of cells (it had exactly one cell, and that cell's child just vanished), it's a different situation: an interior page with zero cells isn't valid — your own TableInteriorPage::from_parts already rejects that — but it's not logically empty, it still represents everything under its rightmost_child. So this level has to collapse: splice itself out of the tree, and whoever pointed at it now needs to point at rightmost_child directly instead.

That's two different things a vanished child can report upward: "I'm just gone, remove me" vs. "I collapsed, but here's who should take my place." One enum variant can carry both:

enum DeleteOutcome {
    Done,
    Emptied(Option<PageNumber>), // None = gone entirely; Some(p) = replace me with p
}

The elegant part: the Some(p) case is exactly the repoint operation you already wrote for insert. repoint_child (find whichever pointer currently targets the old page, swap it to the new one) doesn't care whether "new" arrived via a split or a collapse — you can call it unchanged.

Page::TableInterior(mut ip) => {
    let next = ip.child_of(row_id);
    match self.delete_from(next, row_id)? {
        DeleteOutcome::Done => Ok(DeleteOutcome::Done),
        DeleteOutcome::Emptied(Some(surviving)) => {
            repoint_child(&mut ip, next, surviving)?;   // reused, unmodified
            // ... check if ip itself is now empty, same as below ...
        }
        DeleteOutcome::Emptied(None) => {
            remove_child(&mut ip, next)?;                // new: remove instead of repoint
            // ... check if ip itself is now empty ...
        }
    }
}

The one genuinely tricky bit: removing a child reached via rightmost_child

This is the thing I'd flag as worth slowing down for. Removing a child that was reached through a regular cell is simple — delete that cell, and whatever comes next (the following cell, or rightmost_child) naturally absorbs the key range, since routing is "first cell with row_id ≥ target," no other bookkeeping needed.

But if the vanished child was ip.rightmost_child itself, there's no "next" thing to fall back on — rightmost_child is the last word. The fix: promote the last remaining cell into the rightmost_child slot — pop it off cells, and set rightmost_child = popped_cell.left_child. This is almost the exact inverse of a step TableInteriorPage::split_with already does (where a promoted cell's left_child becomes the left half's new rightmost_child) — same move, opposite direction. Worth writing remove_child as its own small function (parallel to repoint_child, not folded into a generic TablePage::remove) specifically because this asymmetry — "removing via a cell" vs. "removing via rightmost_child" — doesn't exist for the leaf-level, by-sort-key removal at all.

Root handling — shrink_root, mirroring split_root

At the top level:

match self.delete_from(self.root_pn, row_id)? {
    DeleteOutcome::Done => Ok(()),
    DeleteOutcome::Emptied(None) => Ok(()),       // root leaf is empty — that's a perfectly valid state
    DeleteOutcome::Emptied(Some(surviving)) => self.shrink_root(surviving), // balance_shallower
}

shrink_root is split_root run in reverse: read surviving's content, write it over self.root_pn (same page-1-stamping concern — and this is where last session's refactor already pays for itself: Pager::write_page self-stamps the header whenever page_number == 1 unconditionally, so you don't need to rediscover that fix here at all), then leak surviving's now-vacated page number.

What to leave deliberately unfinished, and say so

- Leak every emptied/collapsed page number. No freelist exists yet (that's Subproject 7); don't build one now. Document this exactly as the plan suggests: delete-heavy workloads will grow the file even as the logical dataset shrinks, until Subproject 7 lands.
- No partial-underflow rebalancing. A leaf with one cell left is fine, forever, until it's fully empty. That's the policy, not a bug.
- Decide what a delete of a nonexistent row_id does, and be consistent with insert's convention. Insert already errors on a duplicate key; I'd make delete error on a missing key too, for the same reason — "this operation doesn't apply here" should fail the same way in both directions. Your call, but pick one and keep it consistent.

Verifying it — reuse what you already have

Per the plan's definition of done, this is the exact shape of your Subproject 5 random-insert test, extended: maintain a std::collections::BTreeMap alongside the real tree (you already have the shuffled() xorshift helper — reuse it to pick a pseudo-random subset to delete), apply every insert/delete to both, and after each phase assert cursor.scan()'s output matches the reference map's iteration order exactly, and run check_tree after every delete the same way you already do after inserts. If remove_child's rightmost_child-promotion case has a bug, that's almost certainly where check_tree's depth-consistency or range-bound checks will catch it first — it's exactly the kind of structural mistake that produces a tree that still scans correctly by luck but has a page at the wrong depth or a separator out of range.
