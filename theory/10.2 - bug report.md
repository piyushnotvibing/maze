# SQL Module Bug Report

Scope: `src/sql/ast.rs`, `src/sql/lexer.rs`, `src/sql/parser.rs`, and `src/sql/mod.rs`.

Verification: `cargo test --lib sql::lexer` currently fails three tests:
`create_table_with_multiple_typed_columns`, `create_unique_index_on_table`, and
`type_name_keywords_tokenize_as_data_type_not_identifier`. The parser has no tests,
so the parser bugs below are currently uncaught.

## Root cause

- The parser mixes two token-consumption conventions. `parse_primary` leaves its
  token unconsumed, while many callers blindly call `advance()` afterward; some
  clause parsers consume their first token and others do not. This causes the token
  stream to be consumed one or more tokens too early almost everywhere.
  **Fix:** Adopt one rule: every parse function consumes exactly the tokens it
  recognizes and leaves `pos` at the first unconsumed token. Then remove every
  blind `advance()` after a successful sub-parse.

## parser.rs — statement entry points

- `parse_insert` (parser.rs:145), `parse_select` (175), `parse_update` (207), and
  `parse_delete` (226) each advance once at entry, but `parse_statement` already
  consumed the leading keyword. They eat `INTO`, the first projection, the table
  name, and `FROM` respectively.
  **Fix:** Remove those four entry advances.
- `CREATE UNIQUE INDEX` can never parse. The outer match only matches
  `Token::Index` (parser.rs:99), so a leading `UNIQUE` falls into the error arm;
  the inner `Token::Unique` branch (103) is unreachable.
  **Fix:** Match both `Unique` and `Index` at the outer level and consume them in
  the correct order.
- `parse_statement` does not require `Token::Eof` after the semicolon
  (parser.rs:77-78), so trailing tokens or a second statement are silently
  ignored.
  **Fix:** Expect `Eof` after the semicolon, or loop over statements
  intentionally.
- The fallback error is incomplete: `"parser error: failed to "` (parser.rs:75).
  **Fix:** Include the unexpected token in the message.
- The parser only returns one `Stmt`; if multiple semicolon-separated statements
  are intended, they are ignored.
  **Fix:** Either document single-statement parsing and enforce `Eof`, or add a
  statement loop.

## parser.rs — clauses

- `parse_select` advances again whenever `where_clause`, `order_by`, or `limit`
  is `Some` (parser.rs:184-195), consuming the next clause keyword or the
  semicolon.
  **Fix:** Make each clause parser consume its whole clause and remove these
  conditional advances.
- `parse_select_columns` only accepts identifiers via `extract_id`
  (parser.rs:287), so `SELECT *` fails even though `Token::Star` exists. The
  wildcard check at line 306 is dead code because `extract_id` can never return
  `"*"`.
  **Fix:** Handle `Token::Star` explicitly before identifier parsing and
  represent the wildcard in the AST.
- Alias parsing is broken. After seeing `Token::As`, the code calls
  `extract_id` on the same `As` token without advancing past it
  (parser.rs:292-305 and 338-351).
  **Fix:** Consume `As` first, then extract the alias.
- `parse_select_columns` cannot parse arithmetic projections such as
  `SELECT salary + bonus`, although the lexer tests explicitly cover that input.
  **Fix:** Parse select items as expressions, not just identifiers.
- `parse_order_by` requires `ASC` or `DESC` (parser.rs:485-487), but the grammar
  says the direction is optional. `ORDER BY name` is rejected.
  **Fix:** Default to ascending when no direction token follows.
- `parse_order_by` ignores the result of `advance()` at parser.rs:481 (no `?`).
  **Fix:** Propagate the error, or use `expect` consistently.
- `parse_order_by` leaves `ASC`/`DESC` unconsumed and relies on the caller to
  advance, unlike the other clause parsers.
  **Fix:** Consume the direction inside the function and return with `pos` after
  the clause.
- `parse_limit` never advances past `Token::Limit` (parser.rs:504-507); it
  immediately peeks again and sees `Limit`, so every `LIMIT` fails.
  **Fix:** Advance past `Limit` before reading the integer literal.
- The caller advances after a successful `parse_limit` (parser.rs:193-195),
  which consumes the semicolon.
  **Fix:** Remove the caller advance once `parse_limit` consumes the literal
  itself.
- The negative-limit check is unreachable because the lexer never produces a
  negative `Literal::Int`; `LIMIT -1` arrives as `Operation::Sub` followed by an
  integer and fails earlier.
  **Fix:** Either handle the `Sub` token explicitly or remove the dead check.
- `parse_assignment` advances after `parse_expr` (parser.rs:543 and 565),
  consuming the comma, `WHERE`, or semicolon. Multiple assignments and the
  following `WHERE` therefore break.
  **Fix:** Remove those advances and let `parse_expr` leave `pos` at the
  delimiter.
- `parse_insert` does not validate that `into_columns.len()` matches
  `values.len()` when an explicit column list is present (parser.rs:167-171).
  **Fix:** Add the arity check when `into_columns` is `Some`.
- `parse_values` rejects negative literals such as `VALUES (-1)` because the
  lexer emits `Operation::Sub` before the integer (parser.rs:405-416).
  **Fix:** Accept an optional leading minus before a literal and wrap it in a
  unary negation, or normalize it to a negative `Value`.
- `parse_column_def` ignores the newly added `PRIMARY`, `KEY`, and `UNIQUE`
  tokens despite the doc comment claiming support (parser.rs:241-280).
  `CREATE TABLE t (id INTEGER PRIMARY KEY)` fails at the closing parenthesis.
  **Fix:** Extend the grammar and AST with constraints and parse them, or remove
  the tokens and the misleading comment.
- `parse_column_def`, `parse_columns`, and `parse_select_columns` each require at
  least one item, which is correct for the current grammar, but there is no
  explicit rejection message for an empty list.
  **Fix:** If empty lists are invalid, produce a targeted error; otherwise allow
  them consistently.

## parser.rs — expression grammar

- `parse_not_expr` makes `NOT` mandatory (parser.rs:625), so every expression
  without `NOT` fails. It also discards the `NOT` instead of producing
  `UnaryOp::Not`.
  **Fix:** Make `NOT` optional and wrap the parsed comparison in
  `Expr::Unary(UnaryOp::Not, ...)` when present.
- `parse_or_expr` unconditionally advances after the left operand
  (parser.rs:584), handles only one `OR`, and builds `BinOp::And` for `OR` (595).
  **Fix:** Do not advance blindly; loop while the next token is `Or` and build
  `BinOp::Or`.
- `parse_and_expr` unconditionally advances (parser.rs:605), checks for
  `Token::Or` instead of `Token::And` (610), and handles only one `AND`.
  **Fix:** Loop while the next token is `And` and build `BinOp::And`.
- `parse_comparison` makes a comparison operator mandatory (parser.rs:632), so
  bare expressions such as `WHERE flag` or `WHERE a + b` fail.
  **Fix:** Make the comparison optional per the grammar.
- `parse_comparison` advances unconditionally before and after parsing operands
  and once more at parser.rs:663, consuming the delimiter after the expression
  (`AND`, `OR`, `ORDER`, `LIMIT`, or `;`).
  **Fix:** Remove all blind advances and rely on lookahead.
- `parse_comparison` loops over comparison operators (parser.rs:645-662),
  allowing chained comparisons such as `a = b = c`, which the grammar does not
  define.
  **Fix:** Either restrict it to one comparison or document and implement
  left-associativity deliberately.
- The check `if !op.is_comp_op()` (parser.rs:654) is redundant because
  `extract_comp_op` already guarantees a comparison operator. The error message
  also prints `op1` instead of `op`.
  **Fix:** Remove the redundant check and use the correct variable in the
  message.
- `parse_arith_expr` unconditionally advances after the first term and requires
  exactly one `+` or `-` (parser.rs:669-685). It cannot parse a single term and
  is not left-associative.
  **Fix:** Loop while the next token is `Add` or `Sub`.
- `parse_term` has the same problem: it requires exactly one `*` or `/` and
  cannot parse a single factor (parser.rs:689-705).
  **Fix:** Loop while the next token is `Star` or `Div`.
- `parse_primary` advances after parsing a parenthesized expression and then
  expects `RParen` (parser.rs:731-733), so the closing parenthesis is consumed
  twice.
  **Fix:** Remove the advance and expect `RParen` directly.
- `parse_primary` does not consume the identifier or literal token it matches,
  forcing every caller to advance. This is the source of the systemic
  double-advance problem.
  **Fix:** Make `parse_primary` consume its token and remove the compensating
  advances from its callers.
- `parse_factor` handles only one unary minus, so `--x` is rejected.
  **Fix:** Loop over consecutive minus tokens if nested negation should be
  supported.
- `parse_expr` and all precedence levels treat `Token::Eof` as a normal token and
  can advance past it, producing "parser exhausted tokens" instead of a
  meaningful unexpected-end error.
  **Fix:** Check for `Eof` at the expression entry point and stop before
  advancing past it.

## lexer.rs

- The uppercase `X` match arm (lexer.rs:241-252) intercepts every `X`, including
  the `X` inside `TEXT`, `INDEX`, `MAX`, and a standalone `X`. It then errors
  unless the next character is a quote. This is confirmed by three currently
  failing lexer tests: `create_table_with_multiple_typed_columns`,
  `create_unique_index_on_table`, and
  `type_name_keywords_tokenize_as_data_type_not_identifier`.
  **Fix:** Only treat `X` as a blob prefix when it starts a new token (empty
  identity buffer) and the next character is a quote; otherwise let it fall
  through to normal identifier accumulation. Decide whether lowercase `x` is
  also valid.
- Quote handling uses "buffer is non-empty" to decide whether a quote closes a
  literal. This breaks empty strings and empty blobs: `''` is interpreted as an
  escaped quote outside a string and emits no token; `X''` never emits a blob.
  **Fix:** Track an explicit literal state (none/string/blob) and always close
  and emit the literal on the closing quote, even when its buffer is empty.
- The doubled-quote escape check (lexer.rs:217-223) runs even outside a string or
  blob and writes into `string_literal` even inside a blob.
  **Fix:** Only apply escaping when inside the corresponding literal type.
- An unterminated blob literal (`X'abc` at end of input) is not detected; only
  `is_str_char` is checked after the loop (lexer.rs:288-290).
  **Fix:** Also reject if the blob state is still active at end of input.
- `push_buffers` ignores any leftover `string_literal` or `blob_literal`
  content, silently dropping data in edge cases.
  **Fix:** Assert these buffers are empty at flush points or emit an explicit
  error.
- Keywords are case-insensitive only for all-lowercase or all-uppercase
  spellings; mixed case such as `Select` becomes an identifier. Data type names
  are even stricter and only match uppercase, so `integer` becomes an identifier.
  **Fix:** Normalize the identifier to lowercase before keyword lookup and map
  lowercase type names as well.
- The `"*"` entry in `lookup_sql_keyword` (lexer.rs:311) is dead because `*` is
  tokenized before an identifier can be formed.
  **Fix:** Remove it.
- The `=` match arm (lexer.rs:180) lacks the `!is_blob_char` guard used by every
  other punctuation arm. Current fallback behavior happens to work, but it is
  inconsistent and fragile.
  **Fix:** Add the blob guard or restructure the state handling.
- Blob contents are stored as raw bytes of the source characters rather than
  validated/decoded hex. If `X'...'` is intended to be a hexadecimal blob
  literal, invalid characters are currently accepted silently.
  **Fix:** Define the blob literal format and either decode hex or explicitly
  document that the contents are raw.
- `is_str_char` and `is_blob_char` are independent booleans, so invalid
  combinations are representable (and the empty-literal bug produces one).
  **Fix:** Replace them with a single state enum.

## ast.rs and sql/mod.rs

- `Select.select_columns` is a `HashMap<Column, Column>` (ast.rs:42). This loses
  projection order, collapses duplicate column names, cannot represent
  `SELECT *` naturally, and makes aliases fragile.
  **Fix:** Use an ordered list of select items, each holding an expression or
  column plus an optional alias, with a separate wildcard representation.
- The comment at ast.rs:33-37 says `select_columns = None` for `SELECT *`, but
  the field is not optional.
  **Fix:** Update the comment or change the type to match the intended
  representation.
- `Column` in sql/mod.rs:67-71 is used for three different concepts: table
  definitions (type required), projections (type absent), and assignment
  targets/index columns (name only). This makes invalid states representable.
  **Fix:** Split into separate types such as a column definition, a column
  reference, and a select item.
- `Assignment.column` is a `Column` with `c_type: None` (ast.rs:95-98), which is
  unnecessary indirection.
  **Fix:** Store the column name directly.
- The `Comparison` type alias (ast.rs:103) is unused and misleading because
  assignments and comparisons are not interchangeable.
  **Fix:** Remove it.
- The AST has no representation for column constraints (`PRIMARY KEY`, `UNIQUE`,
  `NOT NULL`), even though the lexer now tokenizes `PRIMARY`, `KEY`, and
  `UNIQUE`.
  **Fix:** Add constraints to the AST and grammar, or remove the unused lexer
  tokens and the parser comment claiming support.
- `Stmt`, `Expr`, `SortDir`, and `Assignment` lack `Debug`/`PartialEq`/`Clone`.
  This makes parser tests and error reporting much harder.
  **Fix:** Derive the traits needed for tests and diagnostics.
- Literals are represented twice: `Expr::Literal` uses `lexer::Literal`, while
  `Insert.values` uses `storage::Value` (ast.rs:5, 30, 63).
  **Fix:** Unify on one representation or add an explicit conversion layer.
- `sql::Column` duplicates `catalog::Column`, but they use different type systems
  (`TypeName` versus storage `DataType`).
  **Fix:** Plan a conversion at the parser/executor boundary or reuse the catalog
  type with a parser-side definition type.
- There are no parser tests at all, which is why the entry-point and expression
  bugs are not caught.
  **Fix:** Fix the three failing lexer tests first, then add parser tests
  covering each statement and expression precedence level.
