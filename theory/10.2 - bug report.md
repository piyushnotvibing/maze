# SQL Module Bug Report

Scope: `src/sql/ast.rs`, `src/sql/lexer.rs`, `src/sql/parser.rs`, and `src/sql/mod.rs`.

**Update:** every claim below has been verified against the current tree, either by
direct tracing or by running a permanent test suite now checked into
`src/sql/lexer.rs` and `src/sql/parser.rs` (`cargo test --lib sql::`). Each bullet
below is tagged:

- **[LIVE]** — confirmed, still present, reproduced by a failing test.
- **[FIXED]** — not reproducible; already resolved since this report was written.
- **[RELOCATED]** — the underlying defect is still real, but it now lives at a
  different call site than the one originally cited.
- **[NEW]** — found during verification, not in the original report.

Current test status: `cargo test --lib sql::` → **198 passed, 41 failed**
project-wide, with every failure inside the new `sql::lexer::tests` /
`sql::parser::tests` modules. Lexer: 26 passed / 6 failed. Parser: 14 passed / 35
failed — every test asserting a *valid* statement parses correctly currently
fails; every test asserting an *invalid* one gets rejected currently passes. Run
the suite directly for the exact up-to-date pass/fail list rather than trusting
this document as it continues to age.

## parser.rs — clauses
- **[LIVE]** `parse_select_columns` still cannot parse arithmetic projections
  (`SELECT salary + bonus`). Confirmed empirically
  (`sql::parser::tests::select_with_arithmetic_projection`), but the fix is
  larger than "parse select items as expressions" alone implies: `Stmt::Select.select_columns`
  is `HashMap<Column, Column>`, which has no field to hold an `Expr` at all.
  **Fix:** this needs the `ast.rs` restructuring below (ordered `Vec` of select
  items, each an expression plus an optional alias) before the parser side can
  even be expressed, not just a parser-side change.

## ast.rs and sql/mod.rs

All of the following are confirmed by direct inspection of the type
definitions (no test needed — these are representability/design claims, not
behavioral ones):

- **[LIVE]** `Column` is still used for three incompatible concepts (table
  definitions with a required type, projections/assignments/index columns with
  none).
  **Fix:** split into a column definition, a column reference, and a select
  item.
- **[LIVE]** `Assignment.column` is still a full `Column` with `c_type: None`
  always — unnecessary indirection.
  **Fix:** store the column name directly.
- **[LIVE]** Literals are still represented twice: `Expr::Literal` uses
  `lexer::Literal`, while `Insert.values` uses `storage::Value`.
  **Fix:** unify on one representation (likely converting `lexer::Literal` →
  `storage::Value` at AST-construction time in `parse_primary`/`parse_values`,
  since `Value` is already the canonical runtime representation) or add an
  explicit conversion layer.
- **[LIVE]** `sql::Column` still duplicates `catalog::Column`, with different
  type systems (`TypeName` vs. storage `DataType`).
  **Fix:** plan a conversion at the parser/executor boundary, or have one
  reuse the other.
