# SQL Module Bug Report

Scope: `src/sql/ast.rs`, `src/sql/lexer.rs`, `src/sql/parser.rs`, and `src/sql/mod.rs`.

**Update:** every claim below has been verified against the current tree, either by
direct tracing or by running a permanent test suite now checked into
`src/sql/lexer.rs` and `src/sql/parser.rs` (`cargo test --lib sql::`). Each bullet
below is tagged:

- **[LIVE]** — confirmed, still present, reproduced by a failing test.
- **[FIXED]** — not reproducible; already resolved since this report was written.
- **[RELOCATED]** — the underlying defect is still real, but it now lives at a
  different call site than the one originally cited.
- **[NEW]** — found during verification, not in the original report.

Current test status: `cargo test --lib sql::` → **198 passed, 41 failed**
project-wide, with every failure inside the new `sql::lexer::tests` /
`sql::parser::tests` modules. Lexer: 26 passed / 6 failed. Parser: 14 passed / 35
failed — every test asserting a *valid* statement parses correctly currently
fails; every test asserting an *invalid* one gets rejected currently passes. Run
the suite directly for the exact up-to-date pass/fail list rather than trusting
this document as it continues to age.

## Root cause

- **[LIVE]** The parser mixes two token-consumption conventions. `parse_primary`
  leaves its token unconsumed, while many callers blindly call `advance()`
  afterward; some clause parsers consume their first token and others do not.
  This causes the token stream to be consumed one or more tokens too early
  almost everywhere.
  **Fix:** Adopt one rule: every parse function consumes exactly the tokens it
  recognizes and leaves `pos` at the first unconsumed token. Then remove every
  blind `advance()` after a successful sub-parse. Fix `parse_primary` first,
  then work upward one precedence layer at a time, re-running the test suite
  after each layer rather than touching all nine functions in one pass.
- **[NEW]** Independent of the above, `parse_statements` (the multi-statement
  entry point) has its own, more immediately severe bug: it unconditionally
  calls `advance()` right after the first statement, consuming what should be
  that statement's semicolon; the subsequent `while` loop's own semicolon check
  then looks at the token *after* the real semicolon and never matches; and the
  trailing `self.expect(Token::Semicolon)` fails because `pos` is already
  sitting on `Eof`. Empirically this blocks **every** statement kind at the top
  level, independent of every other bug in this report — even a bare
  `CREATE TABLE t (id INTEGER);` with no clauses fails with
  `"expected Semicolon but got Eof"`. Reproduced by
  `sql::parser::tests::create_table_single_column` and most other positive
  tests.
  **Fix:** Don't blindly advance after the first statement — check that the
  current token actually is a `Semicolon` before consuming it (mirroring the
  loop's own condition), and only require `Eof` once the loop can no longer
  find a `Semicolon` to continue on.

- **[FIXED]** ~~`CREATE UNIQUE INDEX` can never parse because the outer match

- **[FIXED]** ~~`parse_statement` does not require `Token::Eof` after the

- **[FIXED]** ~~The parser only returns one `Stmt`; multiple semicolon-separated

- **[FIXED]** ~~The fallback error is incomplete: `"parser error: failed to "`.~~

  `"expected CREATE/INSERT/SELECT/UPDATE/DELETE, found {t:?}"`.

## parser.rs — clauses

- **[RELOCATED]** `parse_select` advancing again after `where_clause`/`order_by`/
  `limit` is `Some`. Not in `parse_select` anymore — `parse_where_clause` itself
  now has the blind `advance()` right after `parse_expr()`, unconditionally
  consuming whatever follows the WHERE expression.
  **Fix:** unchanged in substance — remove the blind advance and let the
  expression grammar leave `pos` at the real delimiter.
- **[LIVE, different mechanism]** `SELECT *` still fails, but not because
  `parse_select_columns` only accepts identifiers. `parse_select` already
  special-cases `Token::Star` outside `parse_select_columns` — the bug is that
  this branch never calls `advance()` after recognizing `Star`, so `pos` is
  still on `*` when `expect(Token::From)` runs next. Empirically:
  `"expected From but got Star"`. Reproduced by `sql::parser::tests::select_star`.
  **[NEW]**: as a consequence, the duplicate-check this report originally
  flagged as "dead code" (`if first_col == "*"` inside `parse_select_columns`,
  meant to reject `SELECT *, name`) is in fact *unreachable in both directions*:
  a leading `*` never reaches `parse_select_columns` at all (handled by the
  special case above), and `extract_id` can never produce the string `"*"`
  anyway since `*` always tokenizes to the dedicated `Token::Star`, never
  `Token::Id("*")`. `sql::parser::tests::select_rejects_a_wildcard_combined_with_named_columns`
  currently passes anyway (it errors for an unrelated reason upstream), which
  masks this.
  **Fix:** add `self.advance()?` to the `Star` branch in `parse_select`; decide
  where `SELECT *, name` should actually be rejected now that neither existing
  check can ever fire for it.
- **[LIVE]** Alias parsing still broken — after seeing `Token::As`, the code
  calls `extract_id` on the same, still-unconsumed `As` token. Empirically:
  `"expected identity, found As"`. Reproduced by `sql::parser::tests::select_with_alias`.
  **Fix:** consume `As` first, then extract the alias.
- **[LIVE]** `parse_select_columns` still cannot parse arithmetic projections
  (`SELECT salary + bonus`). Confirmed empirically
  (`sql::parser::tests::select_with_arithmetic_projection`), but the fix is
  larger than "parse select items as expressions" alone implies: `Stmt::Select.select_columns`
  is `HashMap<Column, Column>`, which has no field to hold an `Expr` at all.
  **Fix:** this needs the `ast.rs` restructuring below (ordered `Vec` of select
  items, each an expression plus an optional alias) before the parser side can
  even be expressed, not just a parser-side change.
- **[LIVE]** `parse_order_by` still requires `ASC`/`DESC`; the grammar makes the
  direction optional. Empirically: `"expected ASC/DESC, found Semicolon"`.
  Reproduced by `sql::parser::tests::select_with_order_by_defaults_to_ascending_when_direction_omitted`.
  **Fix:** default to `SortDir::Asc` when no direction token follows.
- **[FIXED]** ~~`parse_limit` never advances past `Token::Limit`.~~ Current code
  does advance past `Limit` before reading the literal; `LIMIT 10` gets past
  this stage fine (it then fails on the top-level `parse_statements` bug, not
  here).
- **[LIVE]** Negative literals in `VALUES` still rejected, since the lexer emits
  `Operation::Sub` before the integer, not a negative `Literal::Int`.
  Empirically: `"expected a literal, found Operation(Sub)"`. Reproduced by
  `sql::parser::tests::insert_accepts_a_negative_literal_value` (named for the
  intended behavior; currently fails).
  **Fix:** accept an optional leading minus before a literal in `parse_values`
  and negate, or normalize it into the `Value` directly.
- **[LIVE]** `parse_insert` still does not validate
  `into_columns.len() == values.len()`. Confirmed by inspection; no such check
  exists. `sql::parser::tests::insert_rejects_arity_mismatch_between_columns_and_values`
  currently passes anyway, but only because an explicit column list plus a
  single value happens to also look like a short values list to something else
  downstream — worth re-checking once the arity check is actually added, since
  this test may be passing for the wrong reason.
  **Fix:** add the arity check when `into_columns` is `Some`.
- **[LIVE]** `parse_column_def` still ignores `PRIMARY`/`KEY`/`UNIQUE` despite
  the doc comment claiming support. Empirically:
  `CREATE TABLE t (id INTEGER PRIMARY KEY);` → `"expected RParen but got Primary"`.
  **Fix:** extend the grammar and AST with constraints and parse them, or strip
  the tokens/misleading comment if constraints are out of scope for now.

## parser.rs — expression grammar

- **[LIVE]** `NOT` is still mandatory, not optional, in `parse_not_expr` — this
  is the single most universally-blocking bug in the file, alongside the
  `parse_statements` semicolon bug. Any WHERE/SET expression not literally
  starting with `NOT` fails immediately. Empirically:
  `"expected Not but got Id(\"id\")"` on a plain `WHERE id = 1`. Reproduced by
  nearly every WHERE/SET test in `sql::parser::tests`.
  **Fix:** make `NOT` optional and wrap the parsed comparison in
  `Expr::Unary(UnaryOp::Not, ...)` only when present.
- **[LIVE, confirmed by inspection only]** `parse_or_expr` builds `BinOp::And`
  for `OR`, and `parse_and_expr` checks `Token::Or` instead of `Token::And`.
  Both visible verbatim in the current code. Not yet reachable through a full
  statement in the test suite — the mandatory-`NOT` bug and the
  mandatory-comparison-operator bug below both fire first on every WHERE
  clause tried — but unambiguous on inspection, and
  `sql::parser::tests::select_with_where_and`/`select_with_where_and_binds_tighter_than_or`
  are written to catch this the moment the earlier blockers are fixed.
  **Fix:** loop while the next token is `Or`/`And` respectively, and stop
  blindly advancing after the first operand.
- **[LIVE]** `parse_comparison` still makes the comparison operator mandatory,
  and `parse_arith_expr`/`parse_term` each still require exactly one `+`/`-` or
  `*`/`/` and cannot parse a single term/factor on its own. This is the second
  universally-blocking bug: even `WHERE NOT id = 1` (which satisfies the `NOT`
  requirement) still fails at `parse_term`, since it unconditionally demands a
  `*`/`/` after its first factor. Empirically: `"expected * or /, found Eq"`.
  Reproduced by `sql::parser::tests::select_with_where_not` and most other
  WHERE tests once past the `NOT` gate.
  **Fix:** loop while the next token is `Add`/`Sub` (`parse_arith_expr`) or
  `Star`/`Div` (`parse_term`); make the comparison operator in
  `parse_comparison` optional per the grammar.
- **[LIVE, confirmed by inspection only]** `parse_comparison`'s `loop` has no
  bound, allowing chained comparisons like `a = b = c`, which the grammar
  doesn't define.
  `sql::parser::tests::select_where_rejects_a_chained_comparison` currently
  **passes**, but only because it never reaches this loop — it fails earlier,
  on the mandatory-`NOT`/mandatory-operator bugs. Worth re-checking once those
  are fixed, since this test may currently be passing for the wrong reason.
  **Fix:** restrict to one comparison, or implement chaining deliberately and
  document it.
- **[LIVE]** The redundant `if !op.is_comp_op()` check inside that loop prints
  `op1` instead of `op` in its error message — confirmed verbatim in the
  current code, including the variable-name mismatch. Unreachable in practice
  since `extract_comp_op` already guarantees a comparison operator.
  **Fix:** remove the dead check; if kept for defense-in-depth, fix the
  variable name.
- **[LIVE]** `parse_primary`'s `LParen` branch still consumes the closing paren
  twice: `advance(); parse_expr(); advance(); expect(RParen)`. Confirmed by
  inspection; not yet reachable end-to-end
  (`sql::parser::tests::select_with_parenthesized_where` currently fails on the
  mandatory-`NOT` bug first).
  **Fix:** remove the middle blind advance; `expect(RParen)` alone is correct.
- **[LIVE]** `parse_primary` still leaves its token (`Id`/`Literal`) unconsumed,
  which is the root cause tying the whole file together — every layer above it
  compensates with exactly one blind `advance()`, which is only sometimes the
  right amount once any one layer changes.
  **Fix:** make `parse_primary` consume its own token on the `Id`/`Literal`
  arms; remove every compensating advance in its callers afterward.

## lexer.rs

- **[FIXED]** ~~The uppercase `X` match arm intercepts every `X`, including the
  one inside `TEXT`, `INDEX`, `MAX`, errors unless the next character is a
  quote.~~ The `X` arm's guard already requires the *next* character to be a
  quote before it fires, so `TEXT`/`INDEX`/a standalone `MAX` fall through
  correctly to normal identifier accumulation. Confirmed by
  `sql::lexer::tests::x_inside_an_ordinary_identifier_is_not_mistaken_for_a_blob_prefix`,
  which passes.
- **[FIXED]** ~~Three lexer tests fail: `create_table_with_multiple_typed_columns`,
  `create_unique_index_on_table`, `type_name_keywords_tokenize_as_data_type_not_identifier`.~~
  All three pass now; type names are already present in `lookup_sql_keyword`.
- **[LIVE]** Quote handling still uses "buffer is non-empty" to decide whether a
  quote closes a literal, breaking empty strings and empty blobs. `''` is
  swallowed as a bogus escape pair outside any open string and emits no token
  at all — confirmed by `sql::lexer::tests::empty_string_literal_emits_an_empty_string_token`
  (currently fails). `X''` is worse than originally described: since
  `blob_literal` is empty, the blob-closing branch is skipped and it falls to
  the generic `else { is_str_char = true; }` arm, leaving **both**
  `is_blob_char` and `is_str_char` true simultaneously — an invalid combination
  — and the call errors out with `"unterminated string literal"` instead of
  producing an empty blob. Confirmed by
  `sql::lexer::tests::empty_blob_literal_emits_an_empty_blob_token` (currently
  fails).
  **Fix:** replace the buffer-emptiness heuristic and the two independent
  booleans with one explicit `enum LiteralState { None, InString, InBlob }`;
  always close and emit on the literal-closing quote regardless of buffer
  content.
- **[LIVE]** The doubled-quote escape check still runs unconditionally on any
  two adjacent quotes, with no guard requiring an already-open string or blob —
  this is the direct cause of the `''` bug above.
  **Fix:** only treat `''` as an escape when a literal is actually open, per the
  state-enum fix above.
- **[LIVE]** An unterminated blob (`X'abc` at EOF) is still not detected — only
  `is_str_char` is checked post-loop, with no equivalent check for
  `is_blob_char`, so the content is silently dropped with `Ok(...)` returned.
  Confirmed by `sql::lexer::tests::rejects_an_unterminated_blob_literal`
  (currently fails).
  **Fix:** also bail if blob state is still active at end of input (falls out
  naturally once both states live in one enum).
- **[LIVE]** `push_buffers` still ignores leftover `string_literal`/
  `blob_literal` content. Confirmed by inspection; its signature only touches
  `identity`/`numeric_literal`.
  **Fix:** assert these are empty at flush points, or make the state-enum fix
  above make this case unrepresentable.
- **[LIVE]** Keywords are still case-insensitive only for pure-lowercase or
  pure-uppercase spellings (`Select` is still read as an identifier); data type
  names are still uppercase-only (`integer` is still an identifier). Confirmed
  by `sql::lexer::tests::mixed_case_keyword_is_recognized` and
  `lowercase_type_name_is_recognized` (both currently fail).
  **Fix:** normalize the identifier to one case before the keyword lookup, and
  add lowercase entries for type names.
- **[LIVE, confirmed by inspection only]** The `"*"` entry in
  `lookup_sql_keyword` is still dead — `*` is always intercepted by its own
  dedicated match arm before `identity` could ever contain it.
  **Fix:** remove it.
- **[LIVE as described, but harmless]** The `=` match arm still lacks the
  `!is_blob_char` guard the other punctuation arms have. Traced through: when
  `=` appears inside an open blob, neither of its own guarded arms matches, so
  it falls to the shared catch-all, whose own `if is_blob_char { ... }` check
  happens to still handle it correctly. Confirmed by
  `sql::lexer::tests::equals_sign_inside_a_blob_literal_is_preserved`, which
  passes today. Inconsistent and fragile, not currently broken.
  **Fix:** add the guard for consistency, or let the state-enum rewrite
  subsume it.
- **[LIVE, confirmed by inspection only]** `is_str_char`/`is_blob_char` are
  still independent booleans, so invalid combinations are representable — the
  `X''` case above is a live instance.
  **Fix:** the same state-enum rewrite already covers this.
- Blob contents are still stored as raw source bytes, not hex-decoded.
  Confirmed by `sql::lexer::tests::blob_literal_with_content`, which currently
  passes under the "raw bytes" interpretation. Still an open design question,
  not a bug: decide whether `X'...'` is meant to be hex and decode it, or
  document that it's raw.

## ast.rs and sql/mod.rs

All of the following are confirmed by direct inspection of the type
definitions (no test needed — these are representability/design claims, not
behavioral ones):

- **[LIVE]** `Select.select_columns` is still `HashMap<Column, Column>` — no
  projection order, collapses duplicate names, represents `SELECT *` as a
  magic `{"*": "*"}` entry rather than a real variant, and is why the
  arithmetic-projection fix above can't be purely parser-side.
  **Fix:** an ordered `Vec` of select items, each an expression plus an
  optional alias, with a separate wildcard variant.
- **[LIVE]** The comment claiming `select_columns = None` for `SELECT *` is
  still stale — the field isn't `Option<...>` at all.
  **Fix:** update the comment or the type.
- **[LIVE]** `Column` is still used for three incompatible concepts (table
  definitions with a required type, projections/assignments/index columns with
  none).
  **Fix:** split into a column definition, a column reference, and a select
  item.
- **[LIVE]** `Assignment.column` is still a full `Column` with `c_type: None`
  always — unnecessary indirection.
  **Fix:** store the column name directly.
- **[LIVE]** The `Comparison` type alias is still unused anywhere in the
  codebase.
  **Fix:** remove it.
- **[LIVE]** The AST still has no slot for column constraints (`PRIMARY KEY`,
  `UNIQUE`, `NOT NULL`) despite the lexer tokenizing `Primary`/`Key`/`Unique`.
  **Fix:** add constraints to the AST and grammar, or remove the unused tokens
  and the misleading doc comment.
- **[FIXED]** ~~`Stmt`, `Expr`, `SortDir`, and `Assignment` lack `Debug`/
  `PartialEq`/`Clone`.~~ Added these derives specifically to make the new
  parser test suite possible — this was blocking, not just inconvenient; there
  was no way to `assert_eq!` an AST without them. `Column` also gained
  `Debug`/`Clone` for the same reason.
- **[LIVE]** Literals are still represented twice: `Expr::Literal` uses
  `lexer::Literal`, while `Insert.values` uses `storage::Value`.
  **Fix:** unify on one representation (likely converting `lexer::Literal` →
  `storage::Value` at AST-construction time in `parse_primary`/`parse_values`,
  since `Value` is already the canonical runtime representation) or add an
  explicit conversion layer.
- **[LIVE]** `sql::Column` still duplicates `catalog::Column`, with different
  type systems (`TypeName` vs. storage `DataType`).
  **Fix:** plan a conversion at the parser/executor boundary, or have one
  reuse the other.
- **[FIXED, differently]** ~~There are no parser tests at all.~~ There are now
  — 49 tests in `sql::parser::tests`, 14 passing / 35 failing, checked in
  permanently. Re-run `cargo test --lib sql::parser` for current status rather
  than trusting any snapshot of pass/fail counts in this document.
